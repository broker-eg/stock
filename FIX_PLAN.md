# Stock Desk — repair plan

Source audit: 2026-10-03. This list concerns defects, unreliable behavior, and friction in existing flows. It is **not** a feature roadmap. Findings below are proven by the current source unless marked **needs runtime check**. No production data was changed for this audit.

## Fix first

| ID | Priority | Problem and impact | Evidence | Done when |
| --- | --- | --- | --- | --- |
| F01 | P1 | **A return cannot contain only some products from a multi-product document.** Selecting an original automatically puts every remaining line in the cart. The remove button is hidden for returns, and zero quantity disables posting. A customer returning one product is forced to return all remaining products. | `src/pages.tsx:1200-1231`, `src/pages.tsx:1459-1466`, `src/pages.tsx:1628-1636` | An admin can select just one line of a multi-line sale or purchase, post that return, and leave the other lines available for later returns. |
| F02 | P1 | **The inventory report can show and export results for old filters while displaying new filter labels.** Changing dates or warehouse updates the controls, badge, and “as of” date immediately, but `stockRows` changes only after **Apply filters** completes. CSV uses those old rows too. A slow response from an earlier request can also overwrite a newer report. | `src/pages.tsx:2847-2864`, `src/pages.tsx:2892-2910`, `src/pages.tsx:2920-2940`, `src/pages.tsx:2971-3009`, `src/pages.tsx:3129-3160` | Screen labels and CSV always describe the same applied query and results; pending or failed queries cannot be mistaken for current results. |
| F03 | P1 | **A completed write can be reported as a failed write.** `run()` awaits the write and then the full refresh inside one `try`. If refresh fails, it shows an error and keeps the form open; retrying can create a duplicate sale, payment, expense, or staff account. | `src/App.tsx:180-193`; transaction handler `src/pages.tsx:1233-1268`; payment handler `src/pages.tsx:2184-2202` | The app distinguishes “saved, but could not reload” from “not saved,” preserves the saved ID where available, and gives a safe refresh/recovery action instead of encouraging a second write. |
| F04 | P1 | **A load failure looks like an access denial.** If the signed-in user's data request fails, `data` stays null and the screen says **Account pending**. The error toast is rendered only inside the normal app shell, so the actual error is invisible there. `getSession()` also has no rejection handler, leaving the loading splash indefinitely if it rejects. | `src/App.tsx:151-178`, `src/App.tsx:200-220`, `src/App.tsx:325-336` | Network/data failures show a visible error and retry; only a confirmed missing or inactive profile shows **Account pending**; session initialization always settles. |
| F05 | P1 | **Records are requested in bulk with no pagination.** One refresh requests all documents with all lines, movements, payments, expenses, attendance records, payroll rows, and journal lines. Reports and contact balances then compute from the returned arrays. As data grows, load time rises; if the API caps returned rows, totals and histories can silently become incomplete (**the current row cap needs runtime check**). Every successful mutation triggers the same full reload. | `src/lib/db.ts:156-215`, `src/App.tsx:146-149`, `src/App.tsx:180-187`; client-side reports `src/pages.tsx:2865-2891` | Large histories remain complete and usable; financial/report totals come from complete server-side queries; a single write does not reload unrelated full histories. Test beyond the configured API row limit. |
| F06 | P1 | **The source has no working version history in this checkout.** Root `.git/` is empty, while `dist/.git/` tracks the generated Pages output. The documented publish process commits only built files, so the app source, migrations, and build instructions cannot be recovered from that repository. | Current filesystem: empty root `.git/`, populated `dist/.git/`; `.gitignore:6-7`; `README.md:20-27`; `AGENTS.md` frontend publishing section | Source and migrations are committed in an appropriate repository with secrets excluded, and the Pages build can be reproduced from a reviewed source revision. Choose public/private visibility before pushing source. |

## Repair the existing workflows

| ID | Priority | Problem and impact | Evidence | Done when |
| --- | --- | --- | --- | --- |
| F07 | P2 | **A paid customer return or prepaid supplier return has no settlement path.** A linked return reverses receivable/payable in the ledger, but the payment RPC allows only money *received from customers* or *paid to suppliers*. The contact form offers both directions even when the selected contact's type makes one invalid. This can leave a credit balance with no way to record the actual refund in the existing flow. | `supabase/migrations/20261003170000_cash_sale_fix.sql:162-198`; `supabase/migrations/20261003140000_initial.sql:307-335`; `src/pages.tsx:2108-2125`, `src/pages.tsx:2184-2212` | A return can be settled to the correct cash/bank account and ledger without an artificial supplier/customer entry; the UI offers only valid actions for the contact. Verify with a paid sale and purchase return. |
| F08 | P2 | **Open quotations and orders have no correction path.** History offers **View** and **Fulfill** only. A mistaken open document cannot be edited or closed from the UI, and it remains in the fulfillment list. | `src/pages.tsx:1660-1738`; open-document behavior `supabase/migrations/20261003170000_cash_sale_fix.sql:148-149` | An admin can correct or close a mistaken open quotation/order with an auditable status, while posted transactions remain immutable. |
| F09 | P2 | **Arabic still has English fragments in two real controls.** The return selector renders raw `sale`/`purchase`, and the account-type selector renders raw enum values (`asset`, `liability`, etc.). The locale check covers `t()` calls and literal JSX text, so it does not catch these dynamic raw values. | `src/pages.tsx:1334-1337`, `src/pages.tsx:2602-2608`; `scripts/check-locales.mjs:75-111` | These controls are fully Arabic in Arabic mode and English in English mode; the locale check catches future untranslated enum labels and composed messages. |
| F10 | P2 | **Dialog and mobile navigation keyboard behavior is incomplete.** The shared modal sets `aria-modal` but does not move focus in, contain focus, restore it, or handle Escape. The mobile menu/close icon buttons have no accessible name, and the backdrop is a clickable `div`. | `src/components/ui.tsx:55-79`; `src/App.tsx:227-238`, `src/App.tsx:282-285` | A keyboard user can open, use, and close each modal/menu without tabbing into the page behind it; icon buttons have spoken labels and focus returns to the opener. |
| F11 | P2 | **Page location is lost on reload and browser Back cannot return to a section.** Navigation lives only in React state and always starts at the dashboard. This is especially disruptive while comparing a report with a transaction or resuming after a connection issue. | `src/App.tsx:142`, `src/App.tsx:194-198`, `src/App.tsx:247-266` | Refresh preserves the current section, and browser Back/Forward follows section navigation on GitHub Pages without a 404. |
| F12 | P2 | **Walk-in sales have no visible payment-account choice.** For a walk-in sale, the account selector is hidden, but the frontend sends the retained `cashAccount` state (initially system cash). The server treats the sale as fully paid. A card/bank walk-in sale can therefore be posted to cash, and a previous account choice can carry over invisibly. | `src/pages.tsx:1110-1116`, `src/pages.tsx:1245-1260`, `src/pages.tsx:1584-1620`; `supabase/migrations/20261003170000_cash_sale_fix.sql:150-156` | A cashier can choose the active cash or bank account for a walk-in payment, and the journal entry uses that account. |

## Suggested order of work

1. Repair report filter/result consistency and save/reload error handling (F02–F04). These can mislead users about financial actions or figures.
2. Repair return selection and settlement, then check posted documents, stock movements, journal balance, and contact statements together (F01, F07, F12).
3. Replace bulk history loading with complete, bounded queries and verify totals above the API row limit (F05).
4. Put the source under version control before further deployment, then address correction and navigation flow (F06, F08, F11).
5. Finish the Arabic and keyboard passes (F09–F10).

This is a source review, not a claim that each path was reproduced against the live Supabase project. F05's API limit and F07's expected refund policy need focused runtime/business checks during implementation. No schema change or deployment is proposed by this document alone.
